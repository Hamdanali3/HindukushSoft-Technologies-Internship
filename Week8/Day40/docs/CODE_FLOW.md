# TaskFlow — Code Flow Walkthrough

This document traces **two real requests** — one through the web (Blade) interface, one through the JSON API — from the moment they hit `public/index.php` to the moment a response leaves the server. The goal is to make the architecture diagram in the main README concrete: not "here's a diagram," but "here's the exact file, the exact method, and the exact line that handles each step."

---

## Trace #1 — Web request: creating a task from the Kanban board

**Scenario:** A logged-in project member fills in the "Add a task" form on a project's Kanban board and clicks *Add*.

### Step 1 — The browser sends the request

```
POST /projects/3/tasks
Cookie: laravel_session=...
X-CSRF-TOKEN: ...
Content-Type: application/x-www-form-urlencoded

title=Write+onboarding+docs&status=todo&priority=high
```

This form lives in `resources/views/projects/show.blade.php`, and posts to a named route generated by Laravel's `route()` helper — `projects.tasks.store` — so the URL is never hardcoded in the view.

### Step 2 — Laravel's HTTP kernel and middleware

Every request passes through the global middleware stack (`TrimStrings`, `ConvertEmptyStringsToNull`, session handling, CSRF verification) before it reaches route-specific middleware. Because this route sits inside the `Route::middleware('auth')->group(...)` block in `routes/web.php`, Laravel's `Authenticate` middleware runs next — it checks the session guard, confirms a logged-in user exists, and injects that user into the request. If there were no valid session, the request would be redirected to `/login` before ever reaching our code.

### Step 3 — Routing resolves to a controller

```php
// routes/web.php
Route::post('/projects/{project}/tasks', [TaskController::class, 'store'])
    ->name('projects.tasks.store');
```

Laravel's **route model binding** automatically converts the `{project}` URL segment into a real `Project` Eloquent instance — by the time our controller method runs, `$project` is not an ID, it is a fully loaded model, already fetched from the database.

### Step 4 — The controller delegates validation

```php
// app/Http/Controllers/TaskController.php
public function store(Request $request, Project $project)
{
    abort_unless($project->hasAccess($request->user()), 403);

    $validated = $request->validate([
        'title'    => ['required', 'string', 'max:255'],
        'status'   => ['required', 'in:todo,in_progress,in_review,done'],
        'priority' => ['required', 'in:low,medium,high'],
        // ...
    ]);

    $task = $project->tasks()->create($validated);

    return redirect()->route('projects.show', $project)
        ->with('status', "Task \"{$task->title}\" added.");
}
```

Two things happen here that matter architecturally:

1. **Access control before validation.** `$project->hasAccess($request->user())` is called from the `Project` model itself, not re-implemented inline — the exact same method the API's `ProjectController` and every `Policy` class call. If this user isn't the project owner and isn't in the `project_user` pivot table for this project, the request is rejected with a 403 before any data touches the database.
2. **Validation rules mirror the database's own constraints.** The `in:todo,in_progress,in_review,done` rule matches the `CHECK`/`ENUM` constraint on the `tasks.status` column defined back on Day 36 — an invalid status can't reach the database even if application-level validation were somehow bypassed, and a bad request is rejected here, at the cheapest possible point, rather than surfacing as a database error later.

### Step 5 — The model layer persists the task

```php
// app/Models/Project.php
public function tasks()
{
    return $this->hasMany(Task::class);
}
```

`$project->tasks()->create($validated)` uses this relationship to automatically set `project_id` on the new `Task` row — the controller never manually assigns the foreign key, which removes an entire class of "forgot to set the parent ID" bugs.

### Step 6 — The response redirects back into the same page

Laravel's `redirect()->route(...)->with('status', ...)` performs a standard **POST-redirect-GET** pattern: the browser is told to `GET /projects/3` next, so a page refresh never re-submits the form. The flash message set with `->with('status', ...)` survives exactly one request via the session, and is picked up by the shared layout:

```blade
{{-- resources/views/layouts/app.blade.php --}}
@if (session('status'))
    <div class="mb-6 rounded-md bg-green-50 ...">{{ session('status') }}</div>
@endif
```

The Kanban board itself (`projects/show.blade.php`) re-renders by grouping the project's tasks by status — `$project->tasks->groupBy('status')` was computed once in the controller's `show` method — so the newly created task appears in the correct column automatically, with zero task-specific rendering logic in the view.

## Trace #2 — API request: fetching a project's tasks

**Scenario:** An external client (mobile app, Postman, etc.) with a valid Sanctum token requests a project's task list, filtered to only `in_progress` tasks.

### Step 1 — The client sends the request

```
GET /api/projects/3/tasks?status=in_progress
Authorization: Bearer 12|aBcDeFgHiJkLmNoPqRsTuVwXyZ...
Accept: application/json
```

### Step 2 — Sanctum authenticates the token, not a session

```php
// routes/api.php
Route::middleware('auth:sanctum')->group(function () {
    Route::get('/projects/{project}/tasks', [TaskController::class, 'index']);
    // ...
});
```

Unlike the web trace, there is no cookie and no CSRF token involved. The `auth:sanctum` guard looks up the bearer token against the `personal_access_tokens` table, resolves it to the `User` that owns it, and attaches that user to the request — functionally equivalent to the web session's job, but entirely stateless.

### Step 3 — The API controller applies the identical authorization rule

```php
// app/Http/Controllers/Api/TaskController.php
public function index(Request $request, Project $project)
{
    $this->authorize('view', $project);

    $tasks = $project->tasks()
        ->with('assignee')
        ->withCount('comments')
        ->when($request->filled('status'), fn ($q) => $q->where('status', $request->status))
        ->latest()
        ->get();

    return TaskResource::collection($tasks);
}
```

`$this->authorize('view', $project)` calls straight into `ProjectPolicy::view()`, which internally defers to the exact same `Project::hasAccess()` method used by the web controller in Trace #1. **This is the architectural point this whole project is built around**: the web layer and the API layer never duplicate an authorization rule — they both call into one shared method on the model, wrapped by a Policy for the API side and a direct call for the web side, but backed by identical logic either way.

The `->with('assignee')` and `->withCount('comments')` calls are deliberate — they eager-load the assignee relationship and pre-count comments in the *same* query, rather than letting Blade or the resource layer trigger a separate query per task later (an N+1 query bug that was actually found and fixed during Day 39's testing pass — see [`Day39/docs/BUGFIXES.md`](../../Day39/docs/BUGFIXES.md), Bug #3).

### Step 4 — API Resources shape the response

```php
// app/Http/Resources/TaskResource.php
public function toArray(Request $request): array
{
    return [
        'id' => $this->id,
        'title' => $this->title,
        'status' => $this->status,
        'priority' => $this->priority,
        'due_date' => $this->due_date?->toDateString(),
        'is_overdue' => $this->isOverdue(),
        'assignee' => new UserResource($this->whenLoaded('assignee')),
        'comment_count' => $this->whenCounted('comments'),
    ];
}
```

This is the step that has no equivalent in the web trace at all. The Eloquent `Task` model is never returned directly as JSON — doing so would leak internal columns, timestamps in the wrong format, or (worse) accidentally expose a related model's sensitive fields. `TaskResource` is an explicit allow-list: only what's declared here reaches the client, and `$this->isOverdue()` calls the *same* business-logic method defined once on the `Task` model that the Blade dashboard view also calls — again, one source of truth, two consumers.

### Step 5 — The JSON response leaves the server

```json
[
  {
    "id": 7,
    "title": "Design homepage hero section",
    "status": "in_progress",
    "priority": "high",
    "due_date": "2026-09-10",
    "is_overdue": false,
    "assignee": { "id": 2, "name": "Ayesha Khan", "email": "ayesha@taskflow.test" },
    "comment_count": 2
  }
]
```

No HTML, no session, no CSRF token — a client on a completely different platform (a native mobile app, a separate React frontend, a CI script) could consume this identically to how a browser consumes the Blade view, because both paths terminate in the same authorized, validated data.

## Why this matters for the presentation

The single sentence I'd want an evaluator to walk away with: **TaskFlow has two front doors (web and API) but exactly one set of rules behind both of them.** Nothing about "what a user is allowed to do" is written twice. That's not an accident — it's the reason `Project::hasAccess()`, the Policies, and the shared Eloquent relationships were built the way they were on Days 36–38, and it's the exact property Day 39's test suite was written to verify (see tests asserting the same 403 behavior against both the web and API surfaces for the same unauthorized user).
